# Audio processing and SSF implementation plan

Add a shared audio routing and processing layer to the Unity runtime, expose it through the player's existing Sound settings, and provide separate listening profiles for desktop speakers, headphones, and cabinet Surround Sound Feedback (SSF). Keep a dry Reference profile as the default so tables retain their authored sound. EQ, compression, and room simulation should solve specific playback problems without changing the physics events, sample selection, pitch, or material response that the table already supplies.

## Scope and current integration points

The first release covers mechanical effects, ball collisions, rolling, table music and callouts, ROM audio, and player UI sounds. It adds bus routing, parametric EQ, optional compression, output limiting, optional room reverb, and a calibrated four-corner SSF output. It does not require a VST host, a DAW, Equalizer APO, DOF, or table-specific audio scripts. Saturation, multiband mastering, automatic room correction, acoustic ray tracing, and multiple independent sound devices are later extensions.

The existing mechanical and rolling implementation supplies positions, authored gain, fades, and pitch. Preserve those semantics, including VPX gain curves and silent Ceramic material pairs. `MechanicalSoundGain` currently applies the player mechanical level to registered sources; `SoundMixerView` already exposes that level alongside integration volume controls. Extend that view and its cabinet input navigation instead of introducing another volume settings path.

`SoundAsset.ConfigureAudioSource` currently assigns an optional Unity `AudioMixerGroup`, but that reference is not a portable routing contract in `SoundAssetPacker`. The default mixer contains Effects, Music, and Callouts groups and no exposed parameters. Packaged clips therefore need a stable bus identity that can be rebound to the runtime mixer after `.vpe` restoration. PinMAME separately exposes borrowed PCM frames and an exclusive playback lease through `IPluginAudioSource` and `IPluginAudioPlaybackControl`; use those contracts to bring ROM playback into the graph without playing it twice.

## What SSF needs

SSF uses separately amplified cabinet exciters, commonly mounted at the front left/right near the flippers and the back left/right near the backbox. Exciters couple sound into the cabinet panels, creating both sound and vibration. Four ordinary speakers can use the same position routing, but do not provide the same tactile response. A common installation reserves a separate stereo pair for ROM and backbox audio and uses a 7.1 sound card for the four cabinet channels plus that pair. This is six active channels, not a four-channel global output mode. Center and LFE are not required for the baseline. [DOFLinx SSF documentation](https://doflinx.github.io/docs/getting-started/11_SSF.html), [Cleveland Software Design VPX configuration](https://pinball-docs.clevelandsoftwaredesign.com/docs/ssf/configuring-vpx/).

Channel labels can be misleading. VPX's current SSF layout uses audio rear left/right for the cabinet front, side left/right for the cabinet back, and front left/right for the backbox. Offer that as a preset, but represent cabinet positions by physical names and verify the actual wiring with a channel test. Never assume a numerical channel index matches a physical jack on every OS and sound card. [VPX spatial audio source](https://github.com/vpinball/vpinball/blob/master/src/audio/SpatialAudio.cpp).

Unity exposes Quad and 7.1 speaker modes, but requesting a mode is not proof that the device outputs those channels: platform behavior can include downmixing or using the native device layout. Verify the effective configuration and the actual outputs. The initial supported cabinet setup is one OS-selected multichannel device; two unrelated USB devices need separate clock management and are outside the first release. [Unity AudioSpeakerMode](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/audiospeakermode).

## Routing and ownership

Introduce stable semantic buses: `mechanical.transients`, `mechanical.rolling`, `game.rom`, `table.music`, `table.callouts`, `table.synthetic`, and `player.ui`. Transients include flippers, bumpers, switches, collisions, ball-ball impacts, ramp transitions, and other discrete mechanical events. Rolling is separate so its sustained energy can be balanced independently. Existing Mechanical/Synthetic flags provide a migration fallback; current component types identify rolling. Preserve authored custom mixer behavior until explicitly migrated, with an editor diagnostic for routes that bypass player processing.

Build the Reference route with unity gain and no inherited ducking, sends or high-pass stage from the old default mixer. Preserve explicitly authored custom processing as part of the source scene's existing sound, but do not attach the old default group's effects to newly rebound packaged sounds. Capture both source-scene and restored-table baselines before migration. The player's Reference acceptance target is the restored-table capture; document differences from authoring mixer routes separately rather than adding them to the player during migration. Keep the processing mixer awake while a table, preview or calibration is active; the existing default mixer suspends below -80 dB, which must not freeze a live reverb tail or meter. Stop and reset the graph explicitly when no session uses it.

Do not promise independent music and speech controls for a ROM that supplies one mixed stream. Present it as ROM/Game audio. Music and Callouts controls apply only to separately authored streams. Integration volume remains owned by that integration; a player ROM processing trim is a distinct, labelled control rather than a second slider secretly writing the same setting.

For cabinet mode, pan each mechanical voice before mixing it into its transient or rolling bus. Both buses carry four logical cabinet channels. Their EQ and linked compression feed a common mechanical group, followed by per-corner calibration EQ/trim and a limiter linked across all four outputs. ROM, table program audio, and UI feed a separate stereo backbox group with its own processing and linked stereo limiter. The final layout matrix maps those six logical channels to the verified device channels; unused channels are zero. Reject accidental mapping overlap in SSF profiles.

```text
Mechanical voice + table position -> four-corner panner -> Transients / Rolling
Transients / Rolling -> bus EQ + linked compression -> Mechanical mix
Mechanical mix -> corner EQ + trim -> linked four-channel limiter -> channel map -> device

ROM / music / callouts / synthetic / UI -> stereo program buses -> Backbox mix
Backbox mix -> output EQ + trim -> linked stereo limiter -> channel map -> device
```

Desktop and headphone modes use a stereo mechanical image and stereo program mix, with an optional room reverb send. Their combined stereo output receives final EQ and limiting after summing so peaks from different buses cannot bypass protection. Processing runs on shared buses and output groups, not as hundreds of individual reverb or compressor components. Reverb returns have a defined route and are included before the relevant final limiter.

Keep authored per-voice gain separate from player bus level, processing makeup gain, and output calibration. Initially retain the existing `MechanicalSoundGain` application and leave the new parent mechanical gain at unity; migrate its ownership only with a versioned change and regression tests proving the existing 0–100% setting is applied exactly once. Reserve internal headroom and meter the signal after EQ boosts, makeup gain, reverb returns, and output trims. Digital limiting does not determine the safe physical power of an amplifier or exciter.

### ROM PCM input

Add a shared Unity audio input adapter that binds ROM resources and acquires their playback lease only after its renderer is ready. Subscribe first, copy borrowed PCM before the callback returns into a preallocated bounded ring buffer, validate channel layout and encoding, and resample when the producer rate differs from the mixer rate. Clear pre-lease samples at a synchronized takeover boundary so previously heard legacy audio is not replayed; guard the lease transition against a concurrent producer callback. PinMAME timestamps can be absent, so sequence numbers and measured buffer occupancy must support discontinuity detection and bounded clock-drift correction. Silence underflow, count overflows, and never accumulate an unbounded backlog to hide a stalled producer.

Add an optional resource capability, provisionally `IPluginAudioPlaybackGainSource`, with a thread-safe `PlaybackGain` accessor. PinMAME exposes its existing `OutputGain` through that capability; its current published PCM is raw, and its legacy gain stage is skipped once playback is leased. The managed adapter snapshots the gain when preparing input or handling a volume change and publishes it through the lock-free native parameter exchange. The native callback reads that snapshot once per output block and applies it exactly once, before its own separately labelled processing trim; it never calls a managed interface accessor. Initialize the first block from the current gain, including zero for a saved mute; smooth subsequent changes and retain the integration as the settings owner. Keep existing `PluginPcmFrame` constructors and the raw PCM contract unchanged. Other providers without the capability use unity playback gain and expose that limitation in Diagnostics instead of claiming integration volume metadata exists.

Feed the adapter into the ROM bus. On pause, flush the ring and discard incoming frames until resume rather than replaying stale audio or reporting intentional pause as an overflow. On stop, table replacement, audio reset, or failure, clear queued samples and release the subscription and lease in a defined order. If another plugin already owns playback, report that the external path is outside VPE's processing rather than stealing the lease or silently adding another output. Verify stereo and mono ROMs in multichannel device mode; the current legacy PinMAME output contains stereo assumptions and must not be relied upon as a generic 7.1 route. Diagnose a legacy path left active in multichannel mode.

## DSP choice and sound quality

Use Unity's native audio plugin interface to wrap a small C++ DSP library, with the same kernels in an offline test harness. Keep Unity's mixer for voice scheduling, grouping, sends, and final delivery. Built-in Unity effects provide a useful comparison and dry fallback, but the shipping chain needs consistent multichannel linking, calibration, metering, and explicit latency control. A plugin host would add binary compatibility and configuration work without solving those requirements.

| Processor | Recommended implementation | Intended improvement |
| --- | --- | --- |
| EQ | Signalsmith DSP biquad filters, with VPE parameter smoothing and validated coefficient changes. | Reduce cabinet resonances and harshness; compensate different speakers without changing recordings. |
| Compressor | A small VPE feed-forward soft-knee compressor, using a shared peak detector and gain envelope for linked channels. | Optional control of excessive dynamic range while preserving impacts. |
| Reverb | Signalsmith Basics `ReverbFloat`, an FDN reverb, wrapped as one stereo auxiliary return. | Subtle room cues for dry desktop/headphone playback. |
| Limiter | Signalsmith Basics `LimiterFloat`, configured explicitly for short lookahead and full channel linking. | Catch digital output peaks after processing and calibration. |

Signalsmith's DSP and Basics project licenses are MIT. The vendored STFX wrapper header separately declares the Boost Software License. Pin Basics, its STFX wrapper, and DSP at exact revisions, with DSP at least 1.3.3 for the reverb; retain both license notices and the Boost license text. Basics supplies reverb and limiting, not a conventional compressor. Configure buffers outside active processing. [Signalsmith DSP](https://github.com/Signalsmith-Audio/dsp), [Basics API](https://github.com/Signalsmith-Audio/basics), [STFX wrapper](https://github.com/Signalsmith-Audio/basics/blob/main/include/stfx/stfx-library.h), [Boost license](https://www.boost.org/LICENSE_1_0.txt).

The limiter defaults to 20 ms attack/lookahead and partial channel linking. Set a proposed 1 ms lookahead and full linking explicitly, report actual sample latency, and validate the ceiling and distortion. Label it sample-peak limiting in dBFS; do not claim true-peak/dBTP performance without oversampled detection and tests. [Limiter implementation](https://github.com/Signalsmith-Audio/basics/blob/main/include/signalsmith-basics/limiter.h), [reverb implementation](https://github.com/Signalsmith-Audio/basics/blob/main/include/signalsmith-basics/reverb.h).

For the compressor, implement the documented feed-forward topology with explicit threshold, ratio, knee, attack, release, and manual makeup gain. Detect the maximum channel magnitude and apply one smoothed reduction to every channel in a linked group. Do not copy plugin code as an unexplained algorithm. The current Faust library contains GPL-3.0-only declarations on several relevant compressor functions despite its general LGPL exception header; that requires function-level consideration before reuse. The permissively labelled `sndfilter` compressor is another candidate, but its source includes automatic makeup and a default 6 ms predelay, plus Chromium-derived provenance to verify. A small purpose-built, tested compressor avoids importing those defaults and supports the required four-channel detector directly. [Faust compressor source](https://github.com/grame-cncm/faustlibraries/blob/master/compressors.lib), [sndfilter compressor source](https://github.com/velipso/sndfilter/blob/master/src/compressor.c).

Before choosing the final reverb and compressor tuning, compare the proposed chain against bypass and Unity's built-in effects using matched output levels. Include single impacts, rapid flipper presses, ramp rolling, multiball, and loud ROM passages. Judge transient clarity, pumping, audible coloration, metallic reverb tails, and CPU cost. A more expensive algorithm or louder preset is not evidence of better sound.

### Processing controls and defaults

EQ offers high-pass and low-pass filters, low/high shelves, and up to four bell bands per bus/output. The simple UI shows Bass, Mid, and Treble; Advanced reveals frequency, gain, Q, filter type, and the complete curve. Use minimum-phase filters for low latency. Bound frequency to the current Nyquist limit, reject non-finite values, and interpolate stable coefficients or crossfade filter states during changes.

Compression is off in Reference. A Night preset can start with a gentle 2:1 ratio, 6 dB knee, approximately 10 ms attack and 120 ms release, with a threshold adjusted during listening tests. These are initial tuning values, not a universal calibration. Makeup gain defaults to zero and automatic makeup is absent in the first release. Keep stereo pairs linked and the four SSF channels fully linked; independent compression would change the perceived position of an impact. Compression and limiting remain separate controls with separate gain-reduction meters.

Reverb is off in Reference and off on the SSF cabinet branch. A Desktop Room preset can start with a short 0.3–0.6 s decay and a low send, then be tuned against the actual recordings, which may already contain room sound. Offer amount, room size/decay, predelay, high-frequency damping, and return width. Use a common room return with separate bus sends; ROM reverb defaults off. No persistent tails remain after unloading a table or muting output. Large hall presets, convolution impulse-response loading, and physical room simulation are deferred.

The limiter is off in Reference to retain a true bypass comparison. Processed presets enable a proposed -1 dBFS sample-peak ceiling, 1 ms lookahead, and an auditioned release. Show the added delay, allow global bypass, and keep limiter delay constant during an active game; changing it requires applying a new audio configuration. A short lookahead is a latency/quality tradeoff, not a promise of transparent limiting under every input. If the library cannot meet the tested ceiling and quality requirements at that delay, change the algorithm or budget explicitly rather than silently using its 20 ms default.

## Spatial rendering and cabinet calibration

### Four-corner panning

Normalize a voice's position in table-local playfield coordinates: `u` runs from left to right, and `v` from the lockbar toward the backbox. Convert from the table's actual coordinate convention once at the boundary; test mirrored, rotated, translated, and scaled table transforms. Ball-ball impacts use the collision position, static mechanisms use their own position, and rolling voices update as the ball moves. Camera motion and screen rotation never change an SSF speaker assignment.

Start with corner gains `sqrt((1-u)*(1-v))`, `sqrt(u*(1-v))`, `sqrt((1-u)*v)`, and `sqrt(u*v)` for front-left, front-right, back-left, and back-right. Clamp the coordinates and smooth moving gains over a short interval. The squared gains sum to one; that is an electrical power convention, not a guarantee of equal perceived loudness through a wooden cabinet. Provide adjustable width/depth response and optional VPX-style response curves after listening comparisons. Maintain a direct low-latency path with no HRTF, Doppler, camera distance attenuation, or room reverb in SSF mode.

For authored stereo mechanical clips, retain stereo playback on desktop; provide an explicit mono fold-down for SSF and flag phase cancellation during authoring. T2's current mechanical clips are mono. A sound without a valid position uses an explicit authored fallback position or centered mechanical image; it must not accidentally route to the backbox.

### Unity routing proof before implementation

The implementation probe corrected an assumption in the original plan. Unity 6000.5 documents spatializer source input as stereo, including mono and multichannel clips; an ordinary spatializer must not depend on receiving eight source channels. The SDK's `UseOutputChannelCount` flag is for ambisonic decoders and cannot expand this ordinary spatializer path. The standalone probe confirms stereo input/output on the available stereo driver, even when the requested configuration reports 7.1. Retain those measurements as a negative control; they do not certify surround output or establish what a different device's mixer will do. [Unity 6000.5 spatializer contract](https://docs.unity.com/en-us/engine/6000.5/manual/audio/mixer-native-audio-plugin/spatializer-sdk), [Unity audio plugin interface](https://github.com/Unity-Technologies/NativeAudioPlugins/blob/master/NativeCode/AudioPluginInterface.h).

Use the planned central native multichannel renderer as the production candidate, with explicit PCM inputs before Unity's per-source upmix and a native generator emitting four cabinet channels and backbox stereo. This decision follows the documented source contract, rather than the absence of cabinet hardware. The prototype's eight-channel generator and post-generator meter measure actual callback counts and channel preservation; setting a generator's declared channel count or requesting 7.1 does not by itself prove an eight-channel output. On this stereo driver the generator and mixer still receive two output channels, so discrete transport and physical output validation remain pending.

The proof must output six distinguishable signals on an actual discrete device, preserve all eight buffer channels through the downstream mixer, keep unused slots silent and avoid a second panning stage. Test standalone playback, input gain/stereo preservation, one channel at a time, moving positions and realistic multiball load. Measure end-to-end impact latency separately. Keep four cabinet outputs fixed in table coordinates regardless of camera position, with no distance attenuation, Doppler or HRTF in SSF mode. Do not implement SSF as ordinary 3D panning plus a Quad setting or assume a mixer group selects a speaker.

The central renderer owns PCM cursors, resampling/pitch, looping, gain/fades and table-position panning behind the routing API. Prototype tone generation is only a transport test and does not implement those voice semantics. Require parity tests for all existing mechanical and rolling behavior before adoption. Feed ROM stereo and authored 2D music/callouts/UI through explicit pre-upmix PCM routes when using that renderer; preserve integration ownership and authoring gain. Desktop processing can proceed independently, but no incomplete SSF path is silently enabled.

### Player setup workflow

Add Sound settings sections for Mix, Processing, Speakers/SSF, and Diagnostics, reachable from both the main menu and the in-game pause menu using the existing keyboard, controller, and cabinet navigation. Basic controls remain useful without opening Advanced.

| Section | User controls |
| --- | --- |
| Mix | Master level, Mechanical, Rolling relative level, ROM/Game integration controls, separately authored Music/Callouts, UI, mute, and per-table balance override. |
| Processing | Reference, Desktop Room, Headphones, Night, Cabinet SSF, and Custom presets; EQ, compression, reverb sends, limiter, bypass comparison, peak and gain-reduction meters. |
| Speakers/SSF | Stereo, ordinary surround where supported, or Cabinet SSF; physical channel assignments, front/back and left/right correction, output trims, per-output EQ, channel tests, and profile save/load. |
| Diagnostics | Requested/effective layout, sample rate, DSP block size, algorithmic delay, underruns, playback owner per ROM stream, native plugin version, whether the selected spatializer is loaded and active, and processing coverage for each bus. |

The SSF wizard first explains that the OS must expose one discrete multichannel device. It requests 7.1 and reads back the configuration, offers the VPX wiring preset, and plays a low-level short test through one channel at a time. The user identifies Backbox Left/Right and the four cabinet corners on a diagram, then balances trims and saves the profile. Tests are bounded in duration and stop immediately on cancel. Keep EQ flat until channel mapping and level balance are confirmed; optional test sweeps help the user identify resonances without claiming automatic calibration.

The pause menu sets `AudioListener.pause`, so preview and channel-test sources explicitly use `ignoreListenerPause` while game voices remain paused. Preview uses controlled test clips or tones, with its own stop/cancel lifecycle, rather than unpausing the table or letting a paused ROM backlog accumulate.

Normal four-speaker surround is a separate mode: it may use camera/listener-relative panning, while SSF is fixed to the cabinet. Headphones initially use stereo spatial playback with optional room ambience. True binaural HRTF rendering is a later step, using a verified cross-platform kernel such as Steam Audio's native API; expose it as a distinct choice rather than calling stereo panning HRTF. Unity selects one project spatializer, and `SetSpatializerPluginName` is Editor-only. Keep any Unity spatializer selection fixed at build time. With the central PCM renderer, a future HRTF kernel belongs behind its own routing API and mode selection; the player cannot promise to swap independent Unity spatializer plugins at runtime. [Steam Audio Unity guide](https://github.com/ValveSoftware/steam-audio/blob/master/unity/doc/guide.rst), [Unity spatializer selection API](https://docs.unity.com/en-us/engine/6000.5/script-reference/unityengine/audiosettings/setspatializerpluginname).

An unplugged or changed device invalidates a cabinet mapping until its layout is revalidated. Mute the cabinet branch and show a clear status if discrete routing is unavailable; allow an explicit switch to stereo rather than letting the OS downmix mechanical effects into the backbox unnoticed. `AudioSettings.Reset` restarts the audio engine and can stop sources and filters. Apply disruptive device/layout changes while paused, rebuild the graph off the audio thread, and restore active loops from current game state when resuming. Preserve a last-known working configuration and provide Revert.

## Settings, authoring, and packaging

Player settings have three layers: portable application listening preferences, hardware-specific output calibration, and optional per-table balance/processing overrides. A hardware profile stores logical speaker assignments, the verified output-layout signature, trims and EQ; it is never embedded in a shared table. With Unity's current default-device API, do not pretend an OS-friendly device name is a stable hardware identifier. Require profile selection or revalidation when identity cannot be established reliably.

Extend `PlayerUserConfig` with a versioned audio section. Use `JsonUtility`-compatible `[Serializable]` classes and lists, not dictionaries; an audio version of zero triggers migration from `mechanicalVolume`, independently of whether the serializer constructs a default audio object. Retain plugin-owned integration settings in their existing stores. Change `PlayerUserConfigStore` explicitly: preserve an unparsable file under a diagnostic name instead of overwriting it with defaults, load a valid backup when available, validate a temporary serialized file, and atomically replace the active file while retaining the last good copy. Table overrides do not modify the imported table. Preset import/export accepts bounded data and known processor identifiers, not executable plugins or DLL paths.

Live preview changes player-owned processing parameters smoothly; Apply persists them and Cancel restores the prior snapshot. Existing integration volume controls keep their current immediate/queued save semantics and are labelled separately, so Cancel does not promise an atomic rollback across plugin configuration stores. Resolve processing values from built-in defaults, the chosen application preset, then explicit per-table overrides; hardware calibration remains a separate final stage. Table recommendations are adopted only by an explicit user action and cannot turn processing on in Reference or override speaker calibration.

Table authors assign semantic buses and may supply optional acoustic recommendations such as reverb sends or a tonal preset. Authors do not assign physical device channels or force the user's cabinet calibration. Runtime code, native DSP binaries, the default mixer and essential presets ship with the engine/player. The assets library may contain reusable recommendation presets and calibration clips, but the core runtime has no dependency on it.

Serialize bus IDs and portable processing recommendations as versioned `.vpe` data with safe defaults for older tables. Rebind all restored sound banks to the runtime routing service; retain unknown IDs as diagnostics and route to a documented compatible fallback. T2 needs no recording changes for this work. Export/reimport it and verify all existing 41 banks and 214 clips, the seven rolling banks, material rows and mechanical/collision components remain intact. Audio processing presets contain data, not arbitrary Unity object references. If a later convolution option includes impulse responses, those become reachable packaged audio assets with explicit ownership and size limits.

## Cross-platform and real-time requirements

Build the same C++ kernels for Windows x64, Linux x64, and macOS x64/arm64, with reproducible native builds and no mandatory platform DSP framework. Keep mobile compatibility in the API and source; Android arm64 and iOS arm64 builds and device tests are a separate delivery gate. Stereo processing can be available there before SSF; never advertise discrete cabinet output on a platform without verified hardware support. Do not base the design on newer Unity audio-foundation features absent from the project's 6000.5 version.

Use preallocated buffers and bounded queues. DSP callbacks perform no managed allocation, file I/O, blocking locks, logging, or Unity main-thread calls. Prepare filter coefficients, buffer resizing, sample-rate changes and graph replacement outside the callback, then exchange immutable parameter snapshots safely. Sanitize invalid samples and parameters, handle denormals, and smooth gain/filter changes to avoid clicks. STFX's guard covers SSE/x64; provide VPE's own ARM64 flush-to-zero handling or denormal-state sanitation and test decaying signals on Apple Silicon and mobile targets. Metering is published to the UI without making the callback wait for it.

Specify lifecycle handling for pause, resume, focus changes, table unload, plugin reload, device reset, and application shutdown. Stop old tails and queues, preserve intentional loop state across graph rebuilds, and ensure stopped mechanisms cannot continue driving exciters. Diagnose externally owned ROM playback rather than claiming it is processed. Extra latency is reported per route, including buffering, resampling and limiter delay; do not equate algorithmic delay with measured end-to-end hardware latency.

## Implementation status

The first routing prototype is implemented as an isolated [native probe and standalone Unity sample](https://github.com/freezy/VisualPinball.Engine/tree/master/VisualPinball.Native~/Audio). It preserves stereo on the available desktop, measures both a spatializer and an eight-channel generator, and records two-channel callbacks even when Unity accepts a 7.1 setting. Unity's documented stereo source contract rules out the original eight-input spatializer assumption; the central generator/PCM renderer is the production candidate. Discrete transport, physical SSF, production buses, processing, packaging changes and player controls remain subsequent gates.

## Delivery sequence

1. **Prove routing and select the backend.** Capture a dry T2 baseline, audit every audio ingress, build the six-output standalone probe, use the documented stereo spatializer contract to select the central generator/PCM renderer candidate, verify its actual mixer/device channel path on a real SSF installation, and record channel order and latency. Prove discrete transport before building the cabinet UI around it. Pin DSP revisions and license notices.
2. **Introduce semantic buses and ROM playback ownership.** Add runtime routing, legacy defaults, `.vpe` rebinding, the PCM input adapter, and gain migration tests. Confirm Reference has unchanged event behavior and no duplicate ROM playback. List any deliberately external paths in Diagnostics.
3. **Add EQ, compression, limiting, and player controls.** Implement offline-tested kernels, native wrappers and meters, global/table settings, live preview/revert, and stereo presets. Tune using matched-level listening comparisons. Keep Reference the migration default.
4. **Add room reverb and portable recommendations.** Wire one stereo auxiliary return, sends, tail management, optional reusable library presets, and `.vpe` round-trip tests. Keep the cabinet mechanical return dry.
5. **Ship SSF calibration.** Connect the proven four-corner renderer, independent backbox route, linked processing, channel mapping, calibration wizard, effective-layout checks, and device-change recovery. Validate T2 on a cabinet with four exciters and separate backbox speakers.
6. **Harden platform coverage and optional spatial modes.** Complete desktop native build/release gates, real-device tests and documentation; then assess HRTF and mobile deployment separately. Multiple physical devices, bass-shaker/LFE routing, convolution, and automatic calibration require their own designs.

Steps 3–4 can be developed for stereo while cabinet hardware testing proceeds, but SSF is not complete until step 5 passes physical output tests. A central-renderer fallback increases step 1–2 scope and needs its own playback parity milestone rather than being hidden inside an effects change. Include music, callouts, synthetic effects and UI voices in that estimate if their stereo signal cannot be recovered after Unity upmixing and they also need a PCM route before upmixing.
